## 2. 採用予定の方針（暫定）

質問への回答により最終確定するが、現時点での提案は以下:

- **Story Breakdown 方式**: **Epic-Based + User Journey 補強**
  - エピックは要件 FR-1〜FR-6 にほぼ 1:1 で対応
  - 各エピック内のストーリーはユーザージャーニー順に並べる
- **Story Format**: 標準フォーマット
  - `As a <persona>, I want <goal>, so that <benefit>.`
- **AC フォーマット**: Given-When-Then（Gherkin風、ただしテストコード化までは要求しない）
- **粒度**: 「1〜2日で実装可能」程度のミドル粒度。粗すぎず細かすぎず。
- **ペルソナ数**: 3〜4（ゲスト/実験者/コミュニティ参加者/AIを信じすぎる人 等）

- A) この 4 ペルソナで進めてよい

## 4. Story Breakdown 方式の比較表（Q3 の参考）

| 方式 | メリット | デメリット | Pandora 適性 |
|------|---------|-----------|--------------|
| User Journey-Based | UX 視点で並ぶ、ナラティブが自然 | 横断ロジックが分散 | ◯ |
| Feature-Based / Epic-Based | 実装単位と一致しやすい、見落としが少ない | UX 体験が見えにくい | **◎** |
| Persona-Based | ペルソナごとの体験が描きやすい | 機能の重複が生まれる | ○ |
| Domain-Based | DDD 的整合性 | MVP には大げさ | △ |
| Epic+Journey ハイブリッド | 実装視点と体験視点を両立 | やや作成コスト高 | **◎** |
